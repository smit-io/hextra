این فورک یک گردش‌کار توسعه بر روی اسکریپت‌های npm نسخه اصلی ارائه می‌کند: یک **Makefile** خودمستند، یک **devcontainer** مبتنی بر Docker Compose با سرور پیش‌نمایش همیشه‌روشن، و ابزارهایی برای **همگام‌سازی با نسخه اصلی**.

<!--more-->

## Makefile

برای فهرست کامل و توضیح‌دار، `make help` را اجرا کنید. هدف‌های مهم، بر اساس گردش‌کار:

### توسعه

| هدف              | چه کاری انجام می‌دهد                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| `make dev`       | سرور توسعه با خط لوله کامل پوسته (در هر بازسازی `hugo_stats.json` را می‌نویسد)                                 |
| `make serve`     | سرور توسعه بدون خط لوله پوسته — راه‌اندازی سریع‌تر وقتی فقط محتوا ویرایش می‌کنید                               |
| `make stats`     | بازتولید `docs/hugo_stats.json` (فهرست کلاس‌هایی که Tailwind برای حذف استایل‌های بلااستفاده به آن تکیه می‌کند) |
| `make css`       | کامپایل CSS تولید — ابتدا آمار را بازتولید می‌کند، پس همیشه درست است                                           |
| `make css-watch` | کامپایل مجدد CSS هنگام تغییر؛ در کنار `make dev` اجرا کنید                                                     |

### نوشتن محتوا

| هدف                                    | چه کاری انجام می‌دهد                                                                                                                       |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `make new-blog NAME=my-post`           | ساخت اسکلت یک نوشته وبلاگ (`docs/content/blog/my-post.md`) به‌صورت پیش‌نویس، با تگ‌ها، نشانگر گزیده و فیلدهای کامنت‌شده نویسنده/کاور/سنجاق |
| `make new-doc NAME=guide/my-page`      | ساخت اسکلت یک صفحه مستندات با عنوان و تگ‌ها؛ `weight` برای جای‌گذاری دستی کامنت‌شده می‌ماند                                                |
| `make new-doc-auto NAME=guide/my-page` | مانند `new-doc`، اما `weight` به‌طور خودکار یکی بیشتر از آخرین صفحه بخش تنظیم می‌شود                                                       |
| `make new-page NAME=showcase/thing`    | ساخت اسکلت هر صفحه‌ای زیر `docs/content/` از طریق آرکتایپ پیش‌فرض                                                                          |

### ساخت و پیش‌نمایش

| هدف            | چه کاری انجام می‌دهد                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `make build`   | بیلد کامل تولید در `docs/public` (ابتدا CSS را کامپایل می‌کند)، بدون پیش‌نویس‌ها — همان چیزی که منتشر می‌شود            |
| `make preview` | بیلد تولید **شامل پیش‌نویس‌ها**، ارائه‌شده توسط کانتینر پیش‌نمایش همیشه‌روشن در [localhost:8043](http://localhost:8043) |

### آزمایش

| هدف                               | چه کاری انجام می‌دهد                                                                                                                                |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `make test`                       | مجموعه کامل Playwright روی یک بیلد تولید تازه و بدون پیش‌نویس                                                                                       |
| `make test-a11y`                  | فقط آزمون‌های دسترس‌پذیری (WCAG 2.2 AA)                                                                                                             |
| `make test-mobile` / `test-build` | مجموعه‌های منوی موبایل و خروجی بیلد                                                                                                                 |
| `make test-preview`               | بازسازی پیش‌نمایش (شامل پیش‌نویس‌ها)، سپس اجرای مجموعه آزمون روی کانتینر پیش‌نمایش زنده — همان چیزی که آزمودید همان است که 8043 همچنان ارائه می‌کند |

### نگهداری

| هدف                                        | چه کاری انجام می‌دهد                                                                |
| ------------------------------------------ | ----------------------------------------------------------------------------------- |
| `make fmt`                                 | اجرای Prettier روی قالب‌ها، CSS و JS                                                |
| `make doctor`                              | عیب‌یابی مشکلات زنجیره ابزار (نسخه‌های Hugo/Node، باینری‌های کهنه)                  |
| `make reset`                               | پاک‌سازی و نصب مجدد `node_modules` — تداخل باینری میزبان/devcontainer را رفع می‌کند |
| `make clean` / `clean-stats` / `clean-all` | حذف خروجی بیلد، تغییرات آمار، یا همه چیز                                            |

{{< callout type="info" >}}
زنجیره وابستگی‌ها اصل ماجراست: `make css` به `stats` وابسته است و `make build` به `css`. اسکریپت‌های خام npm نسخه اصلی از شما می‌خواهند رقص دومرحله‌ای «بازتولید آمار، سپس بیلد CSS» را به خاطر بسپارید ([چرا](https://github.com/smit-io/hextra/blob/main/CLAUDE.md))؛ Makefile آن را در خود کدگذاری می‌کند.
{{< /callout >}}

یک اسکریپت `npm run watch:css` (مختص فورک) نیز وجود دارد که برای علاقه‌مندان به npm، معادل `make css-watch` است.

## اسکلت‌سازی محتوا

هدف‌های `new-*` دور `hugo new` پیچیده شده‌اند، بنابراین Front matter از آرکتایپ‌های `docs/archetypes/`‏ (`blog.md`، `docs.md`، `docs-weighted.md`، `default.md`) می‌آید و فایل موجود به جای بازنویسی، رد می‌شود. `NAME` با یا بدون پسوند `.md` کار می‌کند و مسیرهای تودرتو هم مشکلی ندارند (`NAME=guide/deep/page`).

جزئیاتی که دانستن آن‌ها مفید است:

- **نوشته‌های وبلاگ به‌صورت پیش‌نویس آغاز می‌شوند** (`draft: true`): روی `1313` و `8043` قابل مشاهده‌اند و تا زمانی که این پرچم حذف نشود، از `make build` کنار گذاشته می‌شوند.
- **`new-doc-auto` مقدار `weight` را محاسبه می‌کند** با پویش صفحات موجود پوشه مقصد در لحظه ساخت و افزودن یک واحد به بیشترین مقدار. صفحات پیش‌نویس هم‌ردیف شمرده نمی‌شوند و قراردادهای وزن فاصله‌دار (۱۰، ۲۰، ۳۰…) به ۳۱ می‌رسند، نه ۴۰.
- **فقط انگلیسی** — نسخه‌های ترجمه‌شده (`.fa.md`، `.ja.md`، `.zh-cn.md`) به‌صورت دستی در کنار آن کپی می‌شوند و با چیدمان محتوای موجود مطابقت دارند.

## Devcontainer

نسخه اصلی از یک ایمیج ساده devcontainer استفاده می‌کند. این فورک، devcontainer را با **Docker Compose** ‏(`.devcontainer/docker-compose.yml`) و دو سرویس اجرا می‌کند:

- **`dev`** — ایمیج devcontainer مبتنی بر Go که ویرایشگر شما به آن متصل می‌شود، با مخزن سوارشده در `/workspaces/hextra`. قابلیت‌های devcontainer نسخه Hugo Extended (با نسخه ثابت) و Node 22 را نصب می‌کنند؛ `postCreateCommand` دستور `npm install` را اجرا می‌کند تا کانتینر از اولین باز شدن آماده بیلد باشد. مجموعه‌ای گزیده از افزونه‌های VS Code (Tailwind، Hugo، Prettier، Git Graph، …) از پیش پیکربندی شده است.
- **`preview`** — یک سرور فایل استاتیک بسیار کوچک (~258 kB) به نام (`pierrezemb/gostatic`) که `docs/public` را فقط‌خواندنی ارائه می‌کند، با `Cache-Control: no-store` تا هرگز صفحه کهنه‌ای را عیب‌یابی نکنید. همراه با کانتینر توسعه راه‌اندازی می‌شود و روشن می‌ماند: اجرای مجدد `make build` (یا `make preview`) سایت ارائه‌شده را بدون راه‌اندازی مجدد کانتینر به‌روز می‌کند.

`devcontainer-lock.json` برای نسخه‌های تکرارپذیر ابزارها در مخزن نگه‌داری می‌شود. `.vscode/hextra.code-snippets` هم در کانتینر و هم در یک نسخه معمولی روی میزبان به‌طور خودکار شناسایی می‌شود — [اسنیپت‌های VS Code](vscode-snippets) را ببینید.

یک volume نام‌دار، `node_modules` را درون کانتینر می‌پوشاند، بنابراین کانتینر باینری‌های npm بومی لینوکس خود (مثل `lightningcss`) را نگه می‌دارد و میزبان باینری‌های macOS را — اجرای `npm install` در یک سمت دیگر سمت مقابل را خراب نمی‌کند.

### پورت‌ها

هر دو پورت به‌طور خودکار به میزبان هدایت می‌شوند (`forwardPorts` در `devcontainer.json`):

| پورت   | سرویس                                        | چه چیزی دریافت می‌کنید                |
| ------ | -------------------------------------------- | ------------------------------------- |
| `1313` | سرور توسعه Hugo ‏(`make dev` / `make serve`) | بیلد توسعه با بارگذاری مجدد زنده      |
| `8043` | کانتینر همیشه‌روشن `preview`                 | آخرین بیلد **تولید** از `docs/public` |

این تفکیک اهمیت دارد: `1313` بازسازی‌های زنده سریع می‌دهد، در حالی که `8043` بیلد تولید را نشان می‌دهد — CSS فشرده‌شده، پاک‌سازی‌شده و بدون استایل‌های بلااستفاده. هر دو شامل پیش‌نویس‌ها هستند (`make preview` گزینه `-D` را می‌فرستد تا نوشته‌های منتشرنشده در قالب تولید بررسی شوند)؛ فقط خروجی `make build` بدون پیش‌نویس است. پیش از انتشار، `8043` را بررسی کنید.

{{< callout type="warning" >}}
`make test` و `make build` مقدار `baseURL` پیکربندی را در `docs/public` جاسازی می‌کنند، بنابراین پس از هر کدام، پیش‌نمایش روی `8043` بیلدی را ارائه می‌کند که URLهای مطلق آن به جای دیگری اشاره می‌کنند. برای بازگرداندن آن، `make preview` را دوباره اجرا کنید — یا از `make test-preview` استفاده کنید که خودِ بیلد پیش‌نمایش را می‌آزماید و `8043` را درست باقی می‌گذارد. درون devcontainer، ‏`test-preview` با نام سرویس compose به کانتینر دسترسی دارد (`http://preview:8043`)؛ در نسخه روی میزبان، با `PREVIEW_TEST_URL=http://localhost:8043` جایگزین کنید.
{{< /callout >}}

### باز کردن در کانتینر

VS Code ← ‏«Reopen in Container». اولین باز شدن، Hugo، Node و وابستگی‌های npm را به‌طور خودکار نصب می‌کند.

### توسعه

`make dev` را اجرا کنید و در [localhost:1313](http://localhost:1313) کار را پیش ببرید. هنگام ویرایش استایل‌ها، `make css-watch` را در کنار آن اجرا کنید.

### بررسی بیلد تولید

`make preview` برای تولید بیلد می‌گیرد و نتیجه بلافاصله در [localhost:8043](http://localhost:8043) در دسترس است — بدون راه‌اندازی مجدد سرور، کانتینر پیش‌نمایش صرفاً فایل‌های تازه‌شده را ارائه می‌کند.

## همگام‌سازی با نسخه اصلی

فورک دو هدف Makefile برای دنبال کردن [imfing/hextra](https://github.com/imfing/hextra) اضافه می‌کند:

### `make sync-setup`

سیم‌کشی یک‌باره: ریموت `upstream` را اضافه می‌کند، تگ‌ها را واکشی می‌کند و یک شاخه `upstream-main` به‌صورت آینه **فقط fast-forward** از `upstream/main` می‌سازد. هرگز روی آن کامیت نکنید.

### `make sync-status`

فاصله فعلی را نشان می‌دهد — کامیت‌های عقب‌تر/جلوتر از نسخه اصلی، آخرین تگ نسخه اصلی — و فهرست **فایل‌های متعلق به فورک** را چاپ می‌کند که انتظار می‌رود در هر ادغام تداخل ایجاد کنند:

- `assets/css/styles.css` — پالت‌های تأکیدی/روشن/تاریک
- `assets/css/fonts.css` و `layouts/_partials/google-fonts.html` — فونت‌های Google مختص فورک
- `assets/css/components/*.css` و `layouts/_partials/*.html` — تم‌دهی رنگ تأکیدی
- `static/icons/` — بازسازماندهی فاوآیکون‌ها
- `.devcontainer/`، `Makefile` — ابزارهای مختص فورک

### هر بار فقط یک تگ انتشار را ادغام کنید

تگ‌های `v0.x.y` را یکی‌یکی ادغام کنید، نه اینکه مستقیم به `upstream/main` بپرید — تداخل‌ها کوچک می‌مانند و هر ادغام قابل آزمایش است.

### تداخل‌ها را به نفع توکن‌های فورک حل کنید

وقتی نسخه اصلی اجزای جدیدی اضافه می‌کند، اعمال توکن‌های تأکیدی/پالت روی آن‌ها را بخشی از ادغام کنید (تاریخچه فورک را ببینید: ‏«Apply accent theming to upstream's new components»).

### فایل‌های تولیدی را بازتولید کنید، نه ادغام

`assets/css/compiled/main.css` و `docs/hugo_stats.json` فایل‌های تولیدشده هستند. هرگز تداخل‌های آن‌ها را دستی حل نکنید — یکی از دو طرف را بردارید و سپس `make css` را برای بازتولید اجرا کنید.
